FlexDoc 2.9.9 documentation

Using FlexDoc

FlexDoc is a self-hosted OpenAPI 3.0/3.1 documentation renderer, Try It explorer and browser-local API workspace. This page covers the normal setup and the public 2.9.9 feature surface.

Live demo →API Client →2.9.9 source ↗

Getting started

For React applications, install the canonical client package and its stylesheet:

npm install @prauga/flexdoc-client@2.9.9

For backend frameworks, use the native adapter for your stack. The renderer assets are served locally by the adapter; a FlexDoc account or runtime CDN is not required.

See every framework install command →

Render an OpenAPI document

Pass an OpenAPI 3.0 or 3.1 document to FlexDoc. JSON objects can be imported directly; backend adapters can also point the renderer at a served specification URL.

import { FlexDoc } from '@prauga/flexdoc-client';
import '@prauga/flexdoc-client/styles.css';
import spec from './openapi.json';

export function ApiDocs() {
  return <FlexDoc spec={spec} />;
}

FlexDoc resolves local JSON Pointer references as well as external, nested and circular references. OpenAPI 2.0 / Swagger 2.0 is not accepted; convert it to OpenAPI 3.x first.

Renderer options

Use the options prop to configure the reference UI, initial expansion state, Try It, code samples, themes and other renderer behavior.

<FlexDoc
  spec={spec}
  theme='dark'
  options={{
    title: 'Payments API',
    expand: 'none',
    pathInMiddlePanel: true,
    showRequestHeaders: true,
    tryIt: { enabled: true },
    codeSamples: {
      enabled: true,
      languages: ['curl', 'javascript', 'python', 'go', 'java'],
    },
  }}
/>
expand: 'none' starts endpoint sections collapsed. Viewer Settings can still override the host default for that browser.

Try It

Enable Try It to turn each OpenAPI operation into an executable request editor. Users can edit parameters, request bodies, authentication and the selected server before sending.

<FlexDoc
  spec={spec}
  options={{
    tryIt: {
      enabled: true,
      defaultServer: 'https://staging.api.example.com',
      credentials: 'same-origin',
      requestInterceptor: (request) => ({
        ...request,
        headers: {
          ...request.headers,
          'X-Docs-Client': 'flexdoc',
        },
      }),
    },
  }}
/>

Try It uses the same canonical request model as generated code samples and API Client handoff, including server variables and supported OpenAPI parameter serialization styles.

OpenAPI authentication

Define security schemes in the OpenAPI document as usual. FlexDoc supports Basic and Bearer HTTP authentication, API keys in headers/query/cookies, and OAuth 2.0/OpenID Connect access-token injection.

components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
    apiKeyAuth:
      type: apiKey
      in: header
      name: X-API-Key

security:
  - bearerAuth: []

OpenAPI security alternatives are respected, including OR alternatives and multi-scheme AND requirements. Interactive OAuth grant acquisition lives in the API Client workspace; OpenAPI Try It accepts supplied OAuth/OpenID tokens.

Request code samples

When code samples are enabled, FlexDoc derives them from the same request that Try It builds. The 2.9.9 renderer supports cURL, JavaScript, Python, Go and Java samples.

options={{
  codeSamples: {
    enabled: true,
    languages: ['curl', 'javascript', 'python', 'go', 'java'],
  },
}}

Standalone API Client

Use ApiClient when you want an embeddable HTTP request editor/executor without requiring an OpenAPI document or persisted workspace.

import { ApiClient } from '@prauga/flexdoc-client';
import '@prauga/flexdoc-client/styles.css';

export function RequestPanel() {
  return (
    <ApiClient
      initialRequest={{
        method: 'GET',
        url: 'https://api.example.com/pets',
      }}
      credentials='omit'
      onExecutionComplete={(result) => {
        console.log(result.status, result.responseTime);
      }}
    />
  );
}

The standalone component supports editable URL/query/headers/body/auth, request interceptors, variables, server choices, scripts, tests and response inspection. It does not create collections or persist state by itself.

API Client Workspace

ApiClientWorkspace wraps the same request editor with collections, folders, environments, history, auth inheritance, scripts/tests, Postman import and optional IndexedDB persistence.

import { ApiClientWorkspace } from '@prauga/flexdoc-client';
import '@prauga/flexdoc-client/styles.css';

export function Workspace() {
  return (
    <ApiClientWorkspace
      persistenceKey='payments-api'
      initialRequest={{
        method: 'GET',
        url: '{{baseUrl}}/payments',
        auth: { type: 'inherit' },
      }}
    />
  );
}

The workspace is standalone: it can be used as an API-development surface even when there is no OpenAPI document on the page.

In 2.9.5, normal Send and collection/folder execution share the same canonical request, auth, scripting and variable engine. The collection-runner core is exported for programmatic use and also backs the first-class Run collection / Run folder controls in ApiClientWorkspace.

Collections & folders

Create collections to group saved requests. Folders can be nested to arbitrary depth, and saved requests retain their collection/folder identity for history and replay.

Run collection executes all saved requests in that collection. Run folder includes the selected folder and descendants while excluding collection-root requests. Both preserve workspace.requests saved-request array order; the runner previews that exact queue and the active environment before execution.

Runner items expose pending, running, pass, fail, cancelled and not-run states plus HTTP status, response timing, tests and script/transport errors. Execution is sequential so collection/environment variable mutations from one request are available to later requests.

Stop run aborts the active fetch and marks remaining items not run. Stop on runner failure stops after transport, script or test failure; HTTP status by itself does not define runner failure, so an expected 4xx/5xx can still pass. Script execution is not preemptible by the Stop signal, so a long script phase completes and any completed variable mutations remain applied. A cancelled in-flight request does not create a partial History row.

Use collection-level configuration for shared variables and auth, then override them on a folder or individual request only when necessary.

Variables

Use {{variableName}} placeholders in request URLs, query parameters, headers and bodies. The workspace supplies collection variables and the active environment to the normal request builder.

GET {{baseUrl}}/pets/{{petId}}

Authorization: Bearer {{token}}

At execution time, collection variables are combined with host-provided variables and the active environment. Environment values take precedence when the same key appears in more than one layer.

Template substitution is one pass. FlexDoc does not recursively expand templates inside values.

Structured request bodies

2.9.5 treats URL-encoded, multipart, GraphQL and binary bodies as first-class request-draft modes alongside JSON. Their structured state survives editing, workspace persistence, Postman import, History/replay and normal or collection-run execution.

Multipart boundaries remain browser-owned. File field metadata persists so a user can re-select browser files when the original File object is no longer available; FlexDoc does not pretend imported file paths contain browser-readable bytes.

Response inspection

Responses use one inspection model regardless of browser or host transport. Use Pretty for formatted content, Raw for the unformatted response body, or the sandboxed Preview surface for renderable content.

Post-response scripts/tests, History persistence and collection-run accounting consume the same response snapshot, so host execution does not create a parallel response/test model.

Workspace authentication & OAuth

Collections, folders and requests can use Inherit auth, No auth, Bearer, Basic, API key or OAuth 2.0. In 2.9.5 the canonical auth model also preserves Digest, Hawk, OAuth 1.0, AWS Signature V4, NTLM/Negotiate intent and cookie API keys instead of flattening advanced imported auth into placeholders. The closest explicit child setting still wins; otherwise the request inherits from its parent hierarchy.

OAuth supports manual access tokens, Authorization Code with PKCE, Client Credentials, Password, Implicit and explicit refresh-token reuse. Browser OAuth flows still depend on the provider allowing the relevant redirect and CORS behavior.

OAuth client secrets entered in a browser are not confidential. FlexDoc treats browser-entered credentials as local workspace data, not as a secure secret store.

API-host execution

Browser fetch remains the default executor. Requests that require cookies, a selected server-configured client certificate, Digest, Hawk, OAuth 1.0 or AWS Signature V4 can be capability-routed through the serving Node API host when host execution is explicitly enabled.

setupFlexDoc(app, '/docs', {
  spec,
  options: {
    tryIt: {
      hostExecution: {
        allowedOrigins: ['https://api.internal.example'],
      },
    },
  },
});

The Node backend supports this across Express, Fastify, Hono and Nest/Express integrations. hostExecution: true can also enable it and derive exact allowed origins from OpenAPI servers, but an explicit minimal allowedOrigins list is recommended when the specification is broader than the intended execution surface.

Current Node host capabilities are signed-session cookie jars, server-configured client certificates/mTLS, Digest, Hawk, OAuth 1.0 and AWS Signature V4. NTLM/Negotiate remains represented in workspace/import state but is not advertised by the Node executor in 2.9.5.

Host execution is an SSRF-sensitive server capability, not an open proxy. The execute route inherits docs authentication, requires X-FlexDoc-Execute: 1, exact-origin allowlists destinations, rejects metadata/link-local targets and cross-origin redirects, bounds request/response sizes and timeouts, and never serializes certificate keys/passphrases or server interceptors into the browser.

JVM, .NET, Python, Go, PHP, Ruby, Axum, Actix and Elixir mirror the configuration shape but do not implement host execution in 2.9.5. When explicitly opted in they advertise available: false with no capabilities and register no fake 501 execute route.

Pre-request scripts & response tests

Requests can run trusted JavaScript before execution and tests after the response. The shared flex.* runtime can mutate request data, collection variables and environment variables, record test results and capture console output.

// Pre-request
flex.request.headers.set('X-Run-Id', String(Date.now()));
flex.collection.set('lastRequest', 'pets');

// Post-response tests
flex.test('status is 200', () =>
  flex.expect(flex.response.code).to.equal(200)
);

flex.environment.set(
  'lastPetId',
  String(flex.response.json().id)
);

console.log('tested', flex.response.code);

2.9.5 adds dependency-free, phase-aware IntelliSense for flex.*: dot and Ctrl+Space completion, signatures and documentation, live collection/environment variable keys, response/test APIs only in the appropriate phase, and assertion-chain completion. ArrowUp/ArrowDown changes the active suggestion, Enter or Tab accepts it, Escape dismisses the popup, and Home/End keep normal editor caret movement while suggestions are open.

Scripts are trusted local JavaScript, not a security sandbox. External package imports and a full Postman sandbox API are not provided.

Request history

The workspace keeps bounded request history with resolved execution metadata, response test results, captured script logs and originating collection/folder identity. In 2.9.5 the full History inspector adds search/filtering, persisted response details, tests/logs, replay and deletion.

Completed collection/folder-run requests attach stable run/session metadata so History groups them as one run while retaining per-request inspection. History-oriented failure semantics classify HTTP 4xx/5xx, transport/script errors and failed tests as failed/error outcomes even though runner pass/fail intentionally ignores HTTP status by itself.

History stays bounded to 100 entries. New entries persist response headers and up to 256 KiB of response body; older entries without those optional fields remain readable. Deleted collection/folder provenance remains explicit and replayable through the current workspace fallback. Response data may contain tokens or PII and can be removed by deleting an entry or clearing History. A pre-request script error before a request result exists does not create a History row.

Replaying an entry restores the editable raw request template rather than replacing it with the fully resolved execution URL. This keeps {{variables}} useful after replay.

Postman import

FlexDoc 2.9.5 imports Postman Collection v2.1 JSON and Postman environment JSON directly into the canonical workspace, including structured body modes, cookie API keys and typed Digest, Hawk, OAuth 1.0, AWS Signature V4 and NTLM/Negotiate intent where representable.

  1. Open the API Client Workspace.
  2. Choose Import Postman.
  3. Select a Collection v2.1 JSON file, an environment JSON file, or both.
  4. Review any compatibility warnings and import.

Supported folders, requests, variables, common auth, request bodies and compatible scripts become normal FlexDoc workspace data immediately. There is no separate Postman request engine or persistence layer.

Unsupported auth/sandbox behavior is reported as a warning instead of being silently approximated. Browser File objects cannot be recreated from exported multipart file fields, so those fields require review.

Workspace persistence

By default, ApiClientWorkspace persists browser-local state in origin-scoped IndexedDB. Give each embedded workspace a stable key.

<ApiClientWorkspace persistenceKey='payments-api' />

// Disable persistence entirely:
<ApiClientWorkspace persistenceKey={false} />

Collections, folders, saved requests, variables, environments, auth values, scripts and history are stored as entered. FlexDoc does not encrypt persisted workspace values.

CLI & static export

Use the CLI to serve a local specification with live reload or generate a self-contained static documentation bundle.

npm install --save-dev @prauga/flexdoc-cli@0.4.0

# Serve locally
npx @prauga/flexdoc-cli serve openapi.yaml --watch

# Build static documentation
npx @prauga/flexdoc-cli build openapi.yaml --out ./docs

The generated renderer assets are local to the output; a runtime FlexDoc CDN is not required.

Performance & production readiness

FlexDoc 2.9.9 makes the Node documentation host cost explicit and measurable. Express/setupFlexDoc, Fastify and Hono cache generated host HTML in-process and coalesce concurrent cold requests onto the same render promise instead of serializing the OpenAPI document once per docs request.

Docs HTML retains Cache-Control: no-cache and adds deterministic content-derived ETags. If-None-Match can return 304, and identical spec/options produce identical ETags across independent replicas, so revalidation does not require sticky sessions, Redis or another shared page cache.

Renderer assets stay version-addressed with an immutable one-year cache policy. FlexDoc registers handlers only under the configured docs prefix; the 2.9.9 integration regression suite proves it does not add global middleware to ordinary application API request paths.

# Permanent measured baseline
npm run benchmark:performance

# Published generated-spec cases
~100 KiB · ~1 MiB · ~5 MiB · ~10 MiB

The published Node 22/Linux CI evidence records uncached p50 HTML generation at about 0.19 ms, 3.06 ms, 12.85 ms and 28.28 ms for those four spec sizes respectively, with warm-cache p99 below 0.002 ms in every case. Shared-runner timings are informational evidence rather than hard CI SLAs.

Canonical standalone assets are about 511 KiB JavaScript raw / 151 KiB gzip / 126.6 KiB Brotli and 38.1 KiB CSS raw / 7.6 KiB gzip / 6.5 KiB Brotli. CI enforces deterministic bundle-size ceilings while wall-clock benchmark timing remains informational.

Cached docs HTML is the configured integration snapshot. If an in-memory spec or renderer options change after setup, restart the process until an explicit invalidation API exists. Compression belongs at the application, ingress, CDN or reverse-proxy boundary. For zero application runtime overhead, use the CLI/static export path.

Framework adapters

Backend adapters expose the same renderer contract through native framework routing. They do not implement separate copies of Try It, schemas, API Client behavior or theming.

// Express
import { setupExpressFlexDoc } from '@prauga/flexdoc-backend';

setupExpressFlexDoc(app, '/docs', {
  specUrl: '/openapi.json',
  options: { title: 'My API', expand: 'none' },
});

FlexDoc 2.9.9 publishes the JavaScript client/backend line for Express, Fastify, NestJS and Hono; native adapters remain on their existing independently versioned releases because 2.9.9 does not change canonical renderer bytes or native host code.

Current boundaries

  • OpenAPI 3.0.x and 3.1.x are supported; Swagger/OpenAPI 2.0 is not.
  • Nested deepObject expansion is not recursive.
  • Binary file picking is not yet a first-class renderer control for multipart Try It requests.
  • Webhooks, callbacks, XML metadata and advanced JSON Schema conditionals are not complete first-class interactive surfaces.
  • API Client scripts are trusted local JavaScript rather than a sandbox.
  • Persisted workspace secrets are stored as entered in the browser origin.
  • Postman compatibility is intentionally explicit: unsupported source behavior produces warnings.
