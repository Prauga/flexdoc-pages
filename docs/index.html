FlexDoc 3.3 documentation

Using FlexDoc

FlexDoc is a self-hosted OpenAPI 3.0/3.1 documentation and API workspace. FlexDoc 3.3 keeps the shared renderer, API Client, 3.2 Headless Runner and 3.1 Contract Validation model, then expands controlled API-host execution across supported native runtimes.

Getting started

For React applications, install the 3.3 client package and stylesheet:

npm install @prauga/flexdoc-client@3.3.0

For a backend framework, choose the adapter for that ecosystem. Native packages keep their own semver lines; they are not artificially renumbered to 3.3.0.

Renderer contract v1 remains the compatibility boundary. The package matrix below identifies the source/package set coordinated with product release 3.3.

Architecture

FlexDoc has one canonical browser renderer and one canonical API Client request model. Framework adapters own the OpenAPI document, local renderer assets and backend-only capabilities; they do not reimplement the UI per language.

browser renderer / API Client
        │
        ├── direct browser transport
        │
        └── advertised host transport
              POST <docsPath>/__flexdoc/execute
              X-FlexDoc-Execute: 1

Host execution changes the network transport of the resolved request. Request editing, variables, auth inheritance, scripts, tests, History, collection ordering and response views remain shared.

This is the product boundary that comes from FlexDoc being installed inside the backend: a supported adapter can deliberately expose controlled execution from the service/network context without creating a separate Java, Go, Python, Rust, Ruby, Elixir, PHP or .NET API client.

Renderer, Try It & API Client

The existing product surfaces remain intact in 3.3. The renderer supports OpenAPI 3.0.x/3.1.x, references, server variables, composed/recursive schemas, parameter serialization, generated request samples, Viewer Settings and light/dark/high-contrast appearance.

Try It and the API Client share the same request editor. The workspace adds collections, nested folders, variables/environments, inherited auth, scripts/tests, searchable History, Postman Collection v2.1/environment import, collection/folder runs and portable Runner artifact export.

Request bodies include JSON, raw text, URL-encoded, multipart/form-data, binary and GraphQL modes. Pretty/Raw/Preview, response search, header inspection and copy-as-cURL consume the same normalized response regardless of direct or host transport.

The website Playground is a browser-owned renderer/API Client configurator. It cannot manufacture a backend executor. Host availability is advertised by the backend integration serving FlexDoc.

Backend execution in 3.3

Host execution is off by default on the server. When a serving adapter explicitly enables a real executor and advertises hostExecution.available: true, ordinary interactive API Client sends prefer the API host by default.

This remains true for capabilities: []. An empty list means basic native host transport is available but no advanced host-only capabilities are advertised; it does not mean the client should fall back to browser fetch for every ordinary request.

Reusable collection/headless execution deliberately stays direct by default unless the caller explicitly opts into host semantics or the request requires a host-only capability. Requests requiring unsupported capabilities fail closed.

setupFlexDoc(app, '/docs', {
  spec,
  options: {
    tryIt: {
      hostExecution: {
        allowedOrigins: ['https://api.internal.example'],
        // preferHostExecution: false, // optional Node routing preference
      },
    },
  },
});

On the Node backend, hostExecution: true also enables the executor and can derive exact origins from OpenAPI servers. For production, prefer an explicit allowlist whenever the intended execution surface is narrower than the specification.

# Spring Boot example
flexdoc:
  try-it-host-execution: true
  try-it-host-execution-allowed-origins:
    - https://api.example.com
    - https://staging-api.example.com
X-FlexDoc-Execute: 1 is protocol/cross-site friction only. It is not authentication and is not a CSRF token.

Host-execution security boundary

allowedOrigins is an exact HTTP(S) origin boundary. Private RFC1918/VPC destinations are allowed only when the operator explicitly allowlists the exact origin; link-local and cloud-metadata destinations remain blocked.

Native hardened transports validate the address set and pin the actual connection to validated addresses while retaining the original hostname for HTTP authority, SNI and TLS certificate verification. They revalidate redirect hops and avoid implicit/system proxy routing so a proxy cannot silently bypass destination policy.

  • cross-origin redirects are rejected, even if the second origin is allowlisted;
  • unsafe transport/browser headers and CR/LF-bearing values are rejected or stripped;
  • native execute envelopes are bounded to 32 MiB and returned response bodies to 10 MiB;
  • redirects are bounded to five hops and execution timeouts remain clamped;
  • server-only Node client certificates and interceptors are never serialized into the browser page.
Protect the docs subtree and execute POST with the application's authentication/authorization policy. If documentation auth is cookie based, keep an intentional application CSRF policy. Origin allowlisting and the FlexDoc marker do not identify or authorize the caller.

Operations & abuse controls

Host execution turns an interactive request into browser → API host → target API traffic. Treat that as real CPU, memory, socket, DNS/TLS, bandwidth and target-service load.

FlexDoc's transport safety policy is not a per-user abuse policy. Production deployments should apply caller-aware rate limiting, bound concurrent execute requests, reject overload before unbounded queueing, and monitor execute traffic separately from ordinary documentation requests.

const admission = createHostExecutionAdmission({ maxInFlight: 16 });

app.use('/docs', requireDocumentationUser);
app.use('/docs/__flexdoc/execute', requireSameOriginOrCsrfToken);
app.use(
  '/docs/__flexdoc/execute',
  createHostExecutionAdmissionMiddleware(admission, { retryAfterSeconds: 1 }),
);

The Spring starter similarly exports FlexDocHostExecutionAdmissionFilter; 16 concurrent execute requests per process is the shipped reference starting point, with HTTP 429 and Retry-After: 1 on saturation.

The shared JVM executor has fixed last-resort ceilings of 64 transport workers, 256 queued executions, 256 total Apache connections and 256 connections per route. Those are resource-safety ceilings, not recommended application concurrency.

For multi-replica deployments, user/session quotas belong in a shared gateway or distributed limiter. Useful signals include accepted/rejected requests, in-flight count, p95/p99 duration, timeout/DNS/policy/upstream errors, body sizes, outbound connections/egress, CPU and RSS/PSS.

Headless Runner

The 3.2 Headless Runner remains the portable automation path in 3.3. Export one saved request, folder subtree or collection with its selected environment as a versioned history-free artifact and execute it locally or in CI.

flexdoc run ./pets.flexdoc.json --report ./flexdoc-report.json

The Runner reuses canonical request ordering, variable mutations, inherited auth, pre-request scripts and response tests. HTTP 4xx/5xx alone is not a Runner failure; transport/build errors, script errors and failed flex.test assertions are.

--host consumes an existing advertised host-execution contract; it does not invent a second execute endpoint. Reusable/headless execution remains direct by default unless host semantics are selected or required.

Docs-host --header, --bearer and --basic authenticate the FlexDoc docs/host endpoint only and are never copied to a direct target API request.

Contract Validation

The 3.1 Contract Validation block remains unchanged by 3.3. On supported Node integrations, the running backend produces operation-level findings from runtime discovery and OpenAPI; the renderer and flexdoc validate consume the same backend-owned result.

Findings distinguish undocumented, unobserved, method-mismatched and verified duplicate registrations. Partial discovery stays explicit rather than manufacturing certainty.

Contract Validation can fail CLI/CI by threshold. It does not intercept or block API requests and it does not validate arbitrary request/response payload schemas.

Runtime Intelligence

Runtime Intelligence remains opt-in and observational. Because FlexDoc is installed inside the backend, supported adapters can inspect the application's actual route inventory and compare it with the documented contract.

Current route-discovery support includes Express/Nest on Express, Fastify/Nest on Fastify, Hono, FastAPI/Starlette, ASP.NET Core and Spring MVC. Incomplete discovery is marked incomplete instead of guessed.

Runtime-only routes can reveal intentionally undocumented endpoints. Protect non-public docs before exposing runtime evidence.

Framework adapters

FlexDoc serves the same renderer from Node, .NET, JVM, Python, PHP, Ruby, Go, Rust and Elixir integrations. Renderer support, Runtime Intelligence, Contract Validation and host execution are separate capability axes; installing a renderer adapter does not imply that every backend-only feature is available.

Spring/JAX-RS, ASP.NET Core and the other native host executors require application-owned auth/middleware around the execute route. The 3.3 release specifically names Spring Boot, JAX-RS and ASP.NET Core as integrations without a uniform FlexDoc initialization-time protection acknowledgement; treat application auth configuration as a release requirement when enabling native execution there.

Performance & Host Impact

The existing docs-host baseline still measures documentation generation, bundle size, startup and memory. FlexDoc 3.3 adds a permanent ten-runtime Host Impact workflow with matched direct-versus-host traffic controls.

The baseline tracks latency, throughput, CPU/request, RSS/PSS and cooldown retention so the cost of running execution inside the service remains visible. Managed-runtime PSS is treated as directional investigation context rather than proof of live-object retention.

The benchmark is a release regression control, not a substitute for production telemetry or capacity planning.

Current source APIs & boundaries

The current 3.3 client, CLI and adapter source keeps the 3.2 public Runner APIs while adding a transport contract that is explicitly advertised by the backend serving FlexDoc.

Public client APIs
  • API_CLIENT_RUNNER_ARTIFACT_KIND / API_CLIENT_RUNNER_ARTIFACT_VERSION plus exportApiClientRunnerArtifact, parseApiClientRunnerArtifact and serializeApiClientRunnerArtifact remain public package-root APIs for the versioned, history-free artifacts used by the Runner UI.
  • apiClientCollectionRunName, apiClientCollectionRunRequests and runApiClientCollection remain the canonical runner helpers and preserve saved-request ordering.
  • ApiClientCodeEditor, ApiClientScriptEditor and ApiClientHistoryPage remain exported from @prauga/flexdoc-client for applications that need lower-level product surfaces.
3.3 transport contract
  • FlexDoc 3.3 keeps one API Client state/request model. hostExecution.available: true advertises a working adapter-owned execute endpoint; interactive sends prefer that transport by default, including hosts that advertise capabilities: [].
  • An empty capability list means basic host transport exists, not that host execution is unavailable. Cookie jars, client certificates, Digest, Hawk, OAuth 1.0 and SigV4 remain capability-gated and fail closed when a host does not advertise them.
  • Reusable collection/headless execution keeps direct transport as its default unless host semantics are selected or required. Native adapters must own a real execute binding before they advertise available: true.
CLI/runtime details
  • Runner scripts execute in the CLI process. Variable resolution, pre-request scripts, inherited auth, transport, response tests and collection/environment mutations keep the workspace ordering even when transport is delegated to an advertised host executor.
  • --host loads the existing host-execution advertisement; it does not invent a second route or silently move every reusable request onto the API host.
  • Docs-host --header, --bearer and --basic credentials authenticate the FlexDoc page/execute endpoint only and are never copied onto direct target API requests.
  • flexdoc build writes a .flexdoc-generated marker; replacing an unrelated existing output directory requires --force. External references are bundled into generated output.
  • flexdoc serve --watch rebuilds the root OpenAPI input and live-reloads connected browser pages.

customJs is a generated/standalone host-page hook. The React FlexDoc component applies customCss and accepts root customStyles, but it does not eval options.customJs. The browser Playground therefore exposes CSS/styles/logo configuration and intentionally has no arbitrary JavaScript box.

Runner artifact parsing remains fail-closed: malformed or migration-requiring data, duplicate IDs, out-of-scope entities and in-memory file payloads are rejected rather than silently converted into a different request model.

Current boundaries

  • Host execution is privileged outbound egress from the API host. Enable it only with explicit origins, protected docs and application traffic controls.
  • The first native 3.3 executors provide basic host transport only; advanced cookie-jar, mTLS and signing capabilities remain Node-specific unless explicitly advertised.
  • Flask/Django/WSGI remain renderer-only in the first native 3.3 host-execution slice.
  • NTLM/Negotiate intent is preserved in imported/workspace state but is not executable by current host executors.
  • API Client scripts are trusted local JavaScript, not a security sandbox; saved workspace secrets are stored as entered in the browser origin.
  • Runner artifacts may contain credentials and environment values. Treat them as sensitive configuration.
  • Swagger/OpenAPI 2.0 is not accepted; integrations should provide OpenAPI 3.x.
