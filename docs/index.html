FlexDoc 3.1 documentation

Using FlexDoc

FlexDoc is a self-hosted OpenAPI 3.0/3.1 documentation and API workspace. These docs cover installation, rendering, Try It, the API Client, API-host execution, backend-native Contract Validation, Runtime Intelligence, framework adapters and performance.

Live demo →API Client →3.1 source ↗

Getting started

For React applications, install the client package and its stylesheet:

npm install @prauga/flexdoc-client@3.1.0

For a backend framework, use the adapter for that ecosystem. Each adapter serves the matching FlexDoc renderer, so the UI behaves the same across frameworks.

See every framework install command →

Package versions vary by ecosystem. Renderer contract v1 keeps the current native adapters compatible with the FlexDoc 3.1 renderer.

Architecture

FlexDoc uses one browser renderer across integrations. Node and native framework packages provide the OpenAPI document, renderer options and any backend-only features.

{
  "contractVersion": "1",
  "spec": { "openapi": "3.1.0", "info": {}, "paths": {} },
  "options": {}
}

@prauga/flexdoc-core handles parsing, normalization, request building and code-sample generation. It does not render UI or perform network requests. Adapters ship the renderer assets locally; no FlexDoc CDN is required at runtime.

Contract Validation follows the same architecture rule: supported Node adapters compute operation-level findings inside the running backend, then the renderer and CLI consume that result. They do not maintain separate document-only validators.

Render an OpenAPI document

Pass a parsed OpenAPI 3.0.x or 3.1.x document to FlexDoc. JSON objects can be imported directly; backend adapters can also serve a local or remote specification URL.

import { FlexDoc } from '@prauga/flexdoc-client';
import '@prauga/flexdoc-client/styles.css';
import spec from './openapi.json';

export function ApiDocs() {
  return <FlexDoc spec={spec} />;
}

FlexDoc resolves local JSON Pointer references plus external, nested and circular references. External browser loads still require normal CORS access. Swagger/OpenAPI 2.0 is not accepted; convert it to OpenAPI 3.x first.

Renderer options

FlexDoc accepts spec, a light/dark host-default theme, root customStyles, and options. Options cover page metadata, navigation, expansion, Try It, code samples, localization, theming and Runtime Intelligence.

<FlexDoc
  spec={spec}
  theme='dark'
  options={{
    title: 'Payments API',
    expand: 'none',
    hideHostname: false,
    showRequestHeaders: true,
    tryIt: { enabled: true },
    codeSamples: {
      enabled: true,
      languages: ['curl', 'javascript', 'python', 'go', 'java'],
    },
  }}
/>

Expansion presets are minimal, documentation, interactive, all and none. Explicit expansion sections are parameters, request body, responses, Try It and code samples. Viewer Settings can override those defaults in the browser.

Other controls include tag groups, logo/footer/favicon, topbar/download/hostname visibility, schema ordering, extensions, request-header display, payload sample choice, lazy rendering, scroll offset and locale/message overrides.

Theming & appearance

theme='light' | 'dark' is the host default for FlexDoc. Readers can choose light, dark or high contrast in Viewer Settings; that viewer preference is stored per documentation origin/API title and overrides the host default until it is changed or reset.

<FlexDoc
  spec={spec}
  theme='dark'
  options={{
    theme: {
      colors: {
        primary: { main: '#2563eb' },
        text: { primary: '#172554', secondary: '#475569' },
        border: { light: '#cbd5e1', dark: '#334155' },
      },
      typography: { fontFamily: 'Inter, system-ui, sans-serif' },
      sidebar: {
        backgroundColor: '#f8fafc',
        backgroundColorDark: '#0f172a',
      },
    },
  }}
/>

ApiClientWorkspace has one important standalone distinction: it defaults manageTheme to true, so it owns and persists its workspace theme. If your application should control the workspace appearance, pass manageTheme={false} and drive theme yourself. FlexDoc uses this externally controlled mode for its embedded sibling workspace.

<ApiClientWorkspace
  theme={isDark ? 'dark' : 'light'}
  manageTheme={false}
  persistenceKey='payments-api'
/>

Use the typed ThemeConfig API for brand customization. Legacy preset objects such as themes.material and themes.github are not supported.

Try It

Try It is enabled by default and turns OpenAPI operations into executable requests. Basic and Advanced are two views of the same request editor; Advanced adds scripts, richer auth, environment selection and full response inspection.

<FlexDoc
  spec={spec}
  options={{
    tryIt: {
      enabled: true,
      defaultServer: 'https://staging.api.example.com',
      credentials: 'same-origin',
      requestInterceptor: (request) => request,
    },
  }}
/>

The React-only requestInterceptor can rewrite a browser request before execution. Native adapters cannot accept this JavaScript function through their JSON configuration.

Try It shares the same request builder as generated samples and API Client handoff. Open in API Client moves the live request into the sibling workspace while preserving request values, selected server/custom override, active request tab, script phase and scripts.

Browser security still applies. Cross-origin calls need CORS, forbidden headers such as arbitrary Cookie cannot be set by browser fetch, and browsers may reject GET/HEAD bodies. Supported browser-impossible requests can use explicit API-host execution.

OpenAPI compatibility

FlexDoc supports OpenAPI 3.0.x and 3.1.x and keeps automated compatibility tests for the behavior listed here. Tested areas include JSON/YAML parsing, local/external/circular references, recursive schemas, parameter precedence, server variables, security alternatives, request bodies and request serialization.

AreaStatusNotes
ReferencesTestedLocal, external, nested, circular and external refs back to root.
Servers & parametersTestedServer precedence/variables; form, space/pipe-delimited, flat deepObject, simple/label/matrix, headers/cookies and allowReserved.
SecurityTestedBasic, Bearer, header/query/cookie API keys, supplied OAuth/OpenID tokens and AND/OR requirements.
SchemasTested core / constrained advancedallOf/oneOf/anyOf, recursion, 3.0 nullable, 3.1 null unions, const/enum/defaults/examples and additionalProperties. Pattern/conditional UI remains limited.
Webhooks/callbacks/XMLPartialRepresented in the model where applicable, but not fully interactive.
Flat deepObject properties are supported; nested deep-object structures are not recursively expanded. The source compatibility matrix only marks behavior fully tested when an automated regression covers it.

OpenAPI authentication

Define security schemes in OpenAPI normally. Try It supports Basic and Bearer HTTP authentication, API keys in header/query/cookie locations, and supplied OAuth 2.0/OpenID Connect access tokens.

components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
    apiKeyAuth:
      type: apiKey
      in: header
      name: X-API-Key

security:
  - bearerAuth: []

Security alternatives are respected, including OR alternatives and multi-scheme AND requirements. OpenAPI Try It injects supplied OAuth/OpenID tokens; interactive OAuth grant acquisition lives in the API Client workspace.

Request code samples

Code samples are generated from the exact request currently configured in Try It, so server, parameters, headers, body and auth edits flow into the sample.

options={{
  codeSamples: {
    enabled: true,
    languages: ['curl', 'javascript', 'python', 'go', 'java'],
  },
}}

FlexDoc supports cURL, JavaScript, Python, Go and Java request samples.

Standalone API Client

Use ApiClient for an embeddable HTTP request editor without an OpenAPI document or saved collections.

import { ApiClient } from '@prauga/flexdoc-client';
import '@prauga/flexdoc-client/styles.css';

export function RequestPanel() {
  return (
    <ApiClient
      initialRequest={{ method: 'GET', url: 'https://api.example.com/pets' }}
      credentials='omit'
      onExecutionComplete={(result) => {
        console.log(result.status, result.responseTime);
      }}
    />
  );
}

The standalone editor supports URL/query/headers/body/auth, variables, server choices, interceptors, scripts/tests and the shared response viewer. It does not create collections or persist workspace data by itself.

API Client Workspace

ApiClientWorkspace adds collections, nested folders, environments, inherited auth, scripts/tests, collection and folder runs, History, Postman import and optional browser persistence.

import { ApiClientWorkspace } from '@prauga/flexdoc-client';
import '@prauga/flexdoc-client/styles.css';

export function Workspace() {
  return (
    <ApiClientWorkspace
      persistenceKey='payments-api'
      initialRequest={{
        method: 'GET',
        url: '{{baseUrl}}/payments',
        auth: { type: 'inherit' },
      }}
    />
  );
}

Send and collection/folder runs use the same request, auth, variable and scripting logic. The collection runner is also exported for programmatic use.

Collections, folders & runs

Collections group saved requests. Folders nest arbitrarily and saved requests retain collection/folder identity for execution, History and replay.

Run collection executes all saved requests in that collection. Run folder includes the selected folder and its descendants while excluding collection-root requests. Both preserve saved-request array order and preview the exact queue plus active environment before execution.

Runner rows expose pending, running, pass, fail, cancelled and not-run states plus HTTP status, timing, tests and script/transport errors. Execution is sequential so collection/environment mutations from one request are available to later requests.

Stop run aborts the active fetch and leaves remaining items not run. Stop on runner failure reacts to transport, script or failed-test errors rather than HTTP status alone, so an expected 4xx/5xx response can still be a passing runner item.

Script execution itself is not preempted by the Stop signal. A running script phase completes, including any completed variable mutations. A cancelled in-flight request does not create a partial History row.

Variables

Use {{variableName}} placeholders in URLs, query parameters, headers and bodies. Collection variables, host-provided variables and the active environment are combined when the request is built; active environment values win on key collisions.

GET {{baseUrl}}/pets/{{petId}}

Authorization: Bearer {{token}}

The shared request editor includes URL-variable peek and pre-send missing-key warnings.

Template substitution is one pass. FlexDoc does not recursively expand templates embedded inside variable values.

Structured request bodies

The API Client models none, JSON, raw text, URL-encoded, multipart/form-data, binary and GraphQL bodies as first-class draft modes. Structured state survives editing, persistence, Postman import, History/replay and normal or collection-run execution.

Multipart boundaries remain browser-owned. Imported/exported file paths cannot recreate browser File bytes; FlexDoc preserves re-selectable file metadata and requires the user to choose the actual file again before sending.

Explicit GET/HEAD body state is retained rather than silently discarded. Browser fetch may reject those bodies; supported host execution can send them from the API host.

Response inspection

Browser and API-host execution use the same response format. Pretty formats suitable content, Raw preserves the unformatted body, and Preview renders supported content inside a sandboxed preview.

Response search/filtering, response-header tables and copy-as-cURL are built into the shared response viewer. Post-response tests, History persistence and collection-run accounting all consume the same response snapshot.

Workspace authentication & OAuth

Collections, folders and requests can use Inherit auth, No auth, Bearer, Basic, API key or OAuth 2.0. FlexDoc also preserves Digest, Hawk, OAuth 1.0, AWS Signature V4, NTLM/Negotiate intent and cookie API keys instead of flattening imported auth into placeholders.

The closest explicit child auth setting wins; otherwise a request inherits through folder and collection hierarchy.

OAuth supports manual access tokens, Authorization Code with PKCE, Client Credentials, Password, Implicit and explicit refresh-token reuse. Browser grant flows still depend on provider redirect/CORS behavior.

OAuth client secrets entered in a browser are not confidential. Browser workspace credentials are local data, not a secure secret store.

API-host execution

Browser fetch remains the default. The Node backend can optionally send requests that browsers cannot perform correctly, including cookie jars, configured client certificates/mTLS, Digest, Hawk, OAuth 1.0 and AWS Signature V4.

setupExpressFlexDoc(app, '/docs', {
  spec,
  options: {
    tryIt: {
      hostExecution: {
        enabled: true,
        allowedOrigins: ['https://api.internal.example'],
      },
    },
  },
});

hostExecution: true also enables the Node executor and derives exact allowed origins from OpenAPI servers. In production, use the smallest practical allowedOrigins list when the spec includes more servers than you want FlexDoc to call.

Node support covers Express, Fastify, Hono and Nest integrations. Bearer, Basic, OAuth 2.0 access tokens and header/query API keys can remain on browser fetch when no other host-only capability is selected. Cookie API keys require host execution. NTLM intent is preserved by import/workspace state but is not advertised by the current Node executor.

API-host responses return to the same Pretty/Raw/Preview, scripts/tests, History and collection-run views as browser requests.

Host execution is SSRF-sensitive server functionality, not an open proxy. Node requires explicit opt-in and X-FlexDoc-Execute: 1, exact-origin destinations, HTTP(S), no URL credentials, metadata/link-local blocking before and after DNS resolution, same-origin redirects only, bounded redirects/timeouts/request+response sizes, safe header filtering, bounded signed cookie sessions, and docs authentication on the host routes. Certificate private keys/passphrases and server interceptors are never serialized to the browser.

JVM, .NET, Python, Go, Ruby, PHP, Axum, Actix and Elixir mirror the opt-in configuration boundary but do not implement host execution in 3.1. If explicitly enabled they advertise available: false and register no fake 501 execute route.

Pre-request scripts & response tests

Requests can run trusted JavaScript before execution and tests after the response. The shared flex.* runtime can mutate request data, collection/environment variables, record test results and capture console output.

// Pre-request
flex.request.headers.set('X-Run-Id', String(Date.now()));
flex.collection.set('lastRequest', 'pets');

// Post-response
flex.test('status is 200', () =>
  flex.expect(flex.response.code).to.equal(200)
);
flex.environment.set('lastPetId', String(flex.response.json().id));

The CodeMirror editor provides phase-aware flex.* IntelliSense: dot/Ctrl+Space completion, signatures, live variable keys, response/test APIs and assertion-chain completion. ArrowUp/ArrowDown select suggestions; Enter/Tab accept; Escape dismisses; Home/End retain normal editor caret behavior.

Formatting runs only from Format / Shift+Alt+F, not on blur, and preserves caret/selection.

Scripts are trusted local JavaScript, not a security sandbox. External package imports and the full Postman sandbox API are not provided.

Request history

The workspace keeps request History with test results, script logs and collection/folder context. You can search it, inspect saved responses, browse grouped runs, replay requests and delete entries.

History marks HTTP 4xx/5xx responses, transport/script errors and failed tests as failures. Collection-run pass/fail does not treat HTTP status alone as a runner failure.

History is bounded to 100 entries. New entries persist response headers and up to 256 KiB of body; older entries without those optional fields remain readable. A pre-request script error before a request result exists and a cancelled in-flight runner request do not create partial History rows.

Replay restores the editable raw request template rather than replacing it with the fully resolved execution URL, so {{variables}} remain useful.

Postman import

FlexDoc imports Postman Collection v2.1 and environment JSON into the workspace. Collection/environment files can be selected together; successful files merge even when another selected file fails, and compatibility warnings identify behavior that needs review.

Imports preserve collections, variables, arbitrary nested folders, saved request placement/method/URL/path variables/query/headers, common and advanced auth intent, raw/URL-encoded/GraphQL/multipart/binary body intent and compatible scripts. Postman :pathVariable syntax becomes FlexDoc {{pathVariable}}.

Collection/folder Postman scripts are flattened into each affected request's saved script bundle at import time; they are not retained as shared collection/folder runtime script objects.

Multipart/binary exports contain local file paths, not browser File objects, so file metadata remains reviewable/re-selectable but the bytes must be selected again before sending.

Unsupported sandbox/auth/body behavior produces explicit warnings instead of silent approximation. Treat warnings as part of the import result before executing imported requests.

Persistence & UI preferences

By default, ApiClientWorkspace saves workspace data in origin-scoped IndexedDB. Give each embedded workspace a stable key or disable persistence explicitly.

<ApiClientWorkspace persistenceKey='payments-api' />

// Disable workspace persistence:
<ApiClientWorkspace persistenceKey={false} />

Collections, folders, saved requests, variables, environments, auth values, scripts and History are stored as entered and are not encrypted.

UI preferences are separate lightweight browser preferences. For a persisted workspace, FlexDoc stores sidebar collapse, workspace theme, request tab and script phase in localStorage under the workspace key. FlexDoc viewer preferences similarly persist expansion, sidebar and light/dark/high-contrast appearance per documentation origin/API title.

Programmatic APIs

The client package also exports the parsing, request and execution helpers used by the UI. Useful APIs include:

  • parsing/references: OpenAPIParser, bundleExternalReferences;
  • normalization: normalizeOperation, resolveObject, resolvePathItem, resolveServerVariables;
  • OpenAPI requests: buildRequest, initialRequestValues, parametersFor;
  • API Client requests: buildHttpRequest, inferHttpBodyMode, resolveHttpRequestDraftVariables, requestDraftFromBuiltRequest;
  • execution/runners: executeApiClientRequest, runApiClientCollection;
  • Try It handoff: createOpenApiApiClientSession;
  • scripting/completion helpers and Postman import/merge helpers;
  • code generation: generateCodeSample, languageLabel.

Use the published TypeScript declarations for the complete argument/result types. @prauga/flexdoc-core exposes the framework-neutral parsing/request/code-sample subset without React UI or network execution.

CLI & static export

The CLI serves local JSON/YAML documents or HTTP(S) URLs with external-reference bundling, builds self-contained static documentation, and consumes backend-produced Contract Validation.

npm install --save-dev @prauga/flexdoc-cli@0.6.0

# Serve locally
npx @prauga/flexdoc-cli serve openapi.yaml --watch

# Validate a running Node backend
npx @prauga/flexdoc-cli validate http://127.0.0.1:3000/docs/__flexdoc/runtime

# Build static documentation
npx @prauga/flexdoc-cli build openapi.yaml --out ./docs --base-path /reference/

Static output contains local renderer assets and requires no FlexDoc runtime service or CDN. validate consumes the backend's structured result rather than reimplementing contract comparison in the CLI.

Backend-native Contract Validation

FlexDoc 3.1 adds operation-level Contract Validation on the Node Runtime Intelligence integrations. Express, Fastify, Hono and NestJS produce one structured validation object inside the running backend. The renderer and flexdoc validate parse and integrity-check that same result.

{
  "status": "warn",
  "complete": true,
  "findings": [
    {
      "code": "runtime.operation-undocumented",
      "severity": "warning",
      "location": { "kind": "operation", "method": "POST", "path": "/internal/reindex" }
    }
  ],
  "summary": { "total": 1, "errors": 0, "warnings": 1, "info": 0 }
}

The four stable finding codes are runtime.operation-undocumented, runtime.operation-unobserved, runtime.method-mismatch and runtime.duplicate-operation. Undocumented runtime operations are warnings. Unobserved documented operations and method mismatches become errors only when discovery is complete; absence-based claims are downgraded when discovery is partial.

runtime.duplicate-operation is emitted only where the backend can verify duplicate registrations. In 3.1 that claim is supported for Express, including Nest-on-Express, and Hono. Fastify participates in the other operation-level checks without claiming exact duplicate-registration detection.

Validation status is derived from the findings: fail for any error, warn for warnings without errors, partial when discovery is incomplete without errors/warnings, and pass when complete discovery has no findings.

# Default: fail only when backend status is fail
flexdoc validate http://127.0.0.1:3000/docs/__flexdoc/runtime

# Machine-readable result
flexdoc validate "$FLEXDOC_RUNTIME_URL" --json

# Protected endpoint + stricter CI policy
flexdoc validate "$FLEXDOC_RUNTIME_URL"   --bearer "$FLEXDOC_TOKEN"   --header "X-CI-Run:$GITHUB_RUN_ID"   --fail-on warning

--header <name:value> is repeatable. Protected endpoints also support --bearer and --basic. The default command exits non-zero for backend fail or an unreadable/invalid payload; --fail-on warning makes warnings fail and --fail-on info fails on any finding.

Contract Validation is deliberately narrow in 3.1. It does not validate request/response payload schemas, lint arbitrary OpenAPI rules, inspect live traffic, intercept or reject API requests, run collections, or provide the later headless Runner.

Runtime Intelligence

Runtime Intelligence is off by default. Because FlexDoc is installed inside the backend, supported adapters can inspect routes the application actually registered and compare them with OpenAPI. FlexDoc 3.1 builds Contract Validation on top of that runtime evidence rather than replacing it.

setupExpressFlexDoc(app, '/docs', {
  spec,
  options: {
    runtimeIntelligence: true,
  },
});

Supported hosts expose GET <docsPath>/__flexdoc/runtime. The renderer shows framework/runtime metadata, safe request/server/environment context when available, observed routes, matched operations, runtime-only routes, documented-only routes and whether discovery is complete or partial.

Node: Express/Nest on Express, Fastify/Nest on Fastify and Hono emit both the route-level snapshot and the 3.1 validation object.

FastAPI: setup_fastapi_flexdoc(..., runtime_intelligence=True) inspects the live FastAPI/Starlette route tree and app.openapi(). Runtime Intelligence is not available for Flask, Django or generic ASGI/WSGI in this cut.

ASP.NET Core: set RuntimeIntelligence = true and provide the exact server-side RuntimeOpenApiDocument. FlexDoc reads EndpointDataSource without binding to Swashbuckle/NSwag.

Spring MVC: set flexdoc.runtime-intelligence: true. Runtime comparison uses a FlexDocSpecProvider; spec-location can create one automatically and code-first applications can provide the generated OpenAPI object as a bean.

FastAPI, ASP.NET Core and Spring MVC continue to emit compatible route-level Runtime Intelligence snapshots in 3.1, but they do not yet emit the structured validation object. The renderer keeps route-presence fallback; the CLI intentionally refuses to invent a second validator when validation is absent.

When discoveryComplete is false, documented-only differences may simply be missing from the framework inventory. Runtime-only routes are still useful because FlexDoc observed them directly. Missing prefixes, wildcard expansions and unsupported methods are not guessed.

Safe context is intentionally narrow: no arbitrary environment variables, request headers, filesystem paths, local IP/hostname data, container/cloud metadata or secret-bearing process state. Node uses NODE_ENV; ASP.NET Core uses standard ASP.NET/DOTNET environment variables; Spring uses active profiles; FastAPI omits the environment name because ASGI has no standard equivalent.

Runtime discovery can expose intentionally undocumented endpoints. Node keeps the runtime endpoint under FlexDoc docs authentication; FastAPI, ASP.NET Core and Spring rely on application/proxy protection for the docs subtree.

Request workflow

Try It and the API Client use the same request editor. Moving a request between them keeps its values, selected or custom server, active request tab, script phase and scripts.

The command palette opens operations and common actions such as Overview, Runtime Intelligence, API Client, Settings and Send. Large specs render a bounded result list. Deep links can restore an operation, ?tryIt=1, request tab and script phase.

Request editing adds tab badges, Ctrl/Cmd+Enter Send, saved-request tab restoration, compact pair rows, bulk paste for query/raw headers, URL-variable peek/missing-key warnings and retained GET/HEAD body intent.

The API Client adds clearer request/response separation, response search/filtering, response-header tables, copy-as-cURL, persisted request/script/environment/theme/sidebar state, deletion confirmation, actionable empty states, top-level environment switching and an unsaved-request indicator that remains visible in narrow layouts.

The docs UI also remembers tag/sidebar state, expands matching search groups, downloads JSON/YAML on mobile, copies operation links, ranks useful endpoints on Overview and includes an operation print view.

Accessibility, preferences & localization

Request tabs, script phases and code-sample language tabs implement tablist/tab/tabpanel relationships, aria-controls, roving tabindex and Left/Right/Home/End keyboard behavior. Mobile navigation traps focus while open and restores it on close; hidden-topbar mode retains a navigation path.

High contrast, forced-colors and prefers-reduced-motion are supported. Operation print mode hides application chrome and renders a reader-friendly operation view.

Configurable UI messages cover navigation, environment/theme controls, sidebar labels, Runtime Intelligence, GET/HEAD body guidance and API-host notices. FlexDoc provides the localization API; complete translations are not bundled for every language.

FlexDoc adds no work to ordinary application API requests: runtime integration registers only under the configured docs path and does not install unrelated global request processing. Framework adapters

Backend adapters serve the same FlexDoc renderer through native framework routes. They do not maintain separate Try It, schema, search, code-sample, API Client or theming implementations.

// Express
import { setupExpressFlexDoc } from '@prauga/flexdoc-backend';

setupExpressFlexDoc(app, '/docs', {
  specUrl: '/openapi.json',
  options: { title: 'My API', expand: 'none' },
});

FlexDoc packages use independent version numbers across ecosystems. The install selector lists the current package for each framework; native adapters do not all use version 3.1.0.

Runtime Intelligence is available where an adapter can read a live route inventory: Express/Nest, Fastify/Nest, Hono, FastAPI, ASP.NET Core and Spring MVC. Backend-native 3.1 Contract Validation is the narrower Node capability on Express, Fastify, Hono and NestJS.

Current boundaries

  • 3.1 Contract Validation covers operation-level runtime drift on Express, Fastify, Hono and NestJS; it does not validate request or response schemas and does not reject API requests.
  • flexdoc validate consumes the backend-produced Node validation result; FastAPI, ASP.NET Core and Spring route snapshots do not yet produce that 3.1 validation object.
  • Runtime Intelligence is opt-in and limited to Express/Nest, Fastify/Nest, Hono, FastAPI, ASP.NET Core and Spring MVC.
  • API-host execution is implemented by the Node backend only; other adapters leave those controls unavailable.
  • OpenAPI 3.0.x and 3.1.x are supported; Swagger/OpenAPI 2.0 is not.
  • Nested deepObject expansion is not recursive.
  • Binary file picking is not yet a first-class OpenAPI Try It renderer control for multipart requests.
  • Webhooks, callbacks, XML metadata and advanced JSON Schema conditionals are not fully interactive.
  • API Client scripts are trusted local JavaScript rather than a security sandbox; external package imports/full Postman sandbox compatibility are not provided.
  • Persisted workspace credentials/secrets are stored as entered in the browser origin and are not encrypted.
  • Postman compatibility is explicit: unsupported source behavior produces warnings instead of silent approximation.
